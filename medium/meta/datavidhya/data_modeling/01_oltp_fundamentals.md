# 01 — OLTP Fundamentals

The mental model for OLTP is **single-row writes, point lookups, referential integrity**. The schema is for the *application*. Analytics is downstream. Get this wrong and every query your team writes becomes a 6-way join over a 200-column wide table.

---

## 1. Normalisation (NF1 → 5NF)

Each normal form removes a specific kind of redundancy. The interview question is usually "normalise this denormalised table to 3NF" — so practice the mechanics.

### 1NF — Atomic values, no repeating groups

**Rule:** every cell holds a single value. No arrays, no comma-separated strings, no repeating column groups (`phone1`, `phone2`, `phone3`).

```
BEFORE (violates 1NF)            AFTER (1NF)
┌────┬─────────────┬───────────────┐  ┌────┬─────────────┬───────────────┐
│ id │ name        │ phones        │  │ id │ name        │ phone         │
├────┼─────────────┼───────────────┤  ├────┼─────────────┼───────────────┤
│ 1  │ Alice Wong  │ 555-1234,555 │  │ 1  │ Alice Wong  │ 555-1234      │
│ 2  │ Bob Singh   │ 555-9999     │  │ 1  │ Alice Wong  │ 555-5678      │
└────┴─────────────┴───────────────┘  │ 2  │ Bob Singh   │ 555-9999      │
                                     └────┴─────────────┴───────────────┘
```

You split the multi-valued column into a child table with a 1:N relationship. The original table now has no repeating groups.

### 2NF — No partial dependencies on composite keys

**Rule:** every non-key column must depend on the *entire* primary key, not just part of it. Only matters for tables with composite PKs.

```
BEFORE (violates 2NF)
enrollment(student_id, course_id, student_name, course_title)
   PK = (student_id, course_id)
   student_name → depends on student_id only (partial)
   course_title → depends on course_id only (partial)

AFTER (2NF)
enrollment(student_id, course_id, enrolled_at)
student(student_id PK, student_name)
course(course_id PK, course_title)
```

The non-key attributes that depended on only part of the key are pulled into their own tables.

### 3NF — No transitive dependencies

**Rule:** no non-key column may depend on another non-key column. The classic example:

```
BEFORE (violates 3NF)
employee(id PK, name, dept_id, dept_name, dept_location)
   dept_name, dept_location depend on dept_id (transitive: id → dept_id → dept_name)

AFTER (3NF)
employee(id PK, name, dept_id FK)
department(dept_id PK, dept_name, dept_location)
```

**3NF is the default target for OLTP schemas.** Going further (BCNF, 4NF, 5NF) is rarely worth the join cost.

### BCNF — Every determinant is a candidate key

**Rule:** stricter than 3NF. For every functional dependency X → Y, X must be a superkey.

Classic violation: a table with three columns where two overlapping candidate keys exist.

```
course_teacher(course, teacher, textbook)
   FD1: (course, teacher) → textbook     OK, left side is PK
   FD2: course → textbook                ← course alone determines textbook

BCNF fix:
course(course PK, textbook)
teaching(course, teacher)
```

In practice, BCNF violations in well-modelled schemas are rare. 3NF + a sensible foreign-key strategy covers 95% of real systems.

### 4NF — No multi-valued dependencies

**Rule:** if a row implies two independent multi-valued facts, split them into separate tables.

```
BEFORE (violates 4NF)
person_skill_lang(person, skill, language)
  Alice → Python, SQL
  Alice → English, German
  Cartesian product: 4 rows for Alice alone (Alice/Python/English, Alice/Python/German, ...)

AFTER (4NF)
person_skill(person, skill)
person_language(person, language)
```

4NF matters when you see cartesian blow-up in a junction table.

### 5NF — No join dependencies that aren't implied by candidate keys

Rare in practice. 5NF means the table can only be reconstructed by joining its projections — i.e. it cannot be decomposed further without losing information. Skip unless the interviewer pushes.

## 2. When to denormalise (and why)

Normalise by default. Denormalise **with intent** when one of these is true:

1. **Read latency**: a hot dashboard query joins 8 tables and is hitting your p99. Pre-join and store.
2. **Aggregation cost**: a `COUNT(*)` over a 500M-row table runs every page load. Cache it.
3. **Reporting layer**: you control an analytics read replica — denormalise freely there.
4. **Audit / event log**: append-only history tables can be wide and pre-joined.

**Never denormalise the source of truth.** If you need a denormalised read model, build it as a **separate table populated by triggers, CDC, or batch ETL**.

Rule of thumb: if you find yourself writing `UPDATE table SET x = (SELECT y FROM other WHERE ...)` — you have a denormalisation that needs a trigger or a pipeline, not a synchronous UPDATE.

## 3. Primary keys, foreign keys, surrogate vs natural keys

### Surrogate keys

Synthetic values generated by the database. Never reused. Never meaningful outside the system.

```sql
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

**Pros:** stable across schema changes, small fixed size, no business logic, easy joins.
**Cons:** adds a column, opaque in logs.

### Natural keys

Real-world identifiers that are unique by themselves (`email`, `ISO country code`, `SKU`).

**Pros:** meaningful, self-documenting, no extra column.
**Cons:** can change (yes, even emails), may be long, can collide across systems.

**Default choice: surrogate key + UNIQUE constraint on the natural key.**

```sql
CREATE TABLE users (
    id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email      TEXT NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### Foreign keys

```sql
ALTER TABLE posts
    ADD CONSTRAINT posts_author_fk
    FOREIGN KEY (author_id) REFERENCES users(id) ON DELETE CASCADE;
```

`ON DELETE` choices:

| Action      | Behaviour                                                | Use when                              |
| ----------- | -------------------------------------------------------- | ------------------------------------- |
| `RESTRICT`  | Block the delete if children exist                       | Default — safe                        |
| `CASCADE`   | Delete children automatically                            | Owned children (e.g. `post → likes`)  |
| `SET NULL`  | Set the FK column to NULL                                | Optional relationships                |
| `SET DEFAULT` | Set the FK column to its DEFAULT                       | Almost never                           |
| `NO ACTION` | Same as RESTRICT but deferrable                          | Use inside the same transaction       |

**Always create an index on every FK column** — PostgreSQL does NOT do this automatically.

## 4. Indexing strategy

### B-tree (default)

The workhorse. Good for equality and range queries (`=`, `<`, `>`, `BETWEEN`, `LIKE 'abc%'`).

```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);
```

### Composite indexes

Order matters. Put the most selective / most-filtered column first.

```sql
-- Query: WHERE user_id = ? AND status = 'paid' ORDER BY created_at DESC
CREATE INDEX idx_orders_user_status_created
    ON orders(user_id, status, created_at DESC);
```

The index can serve queries on `(user_id)` or `(user_id, status)` alone, but **not** on `(status)` alone.

### Covering indexes (INCLUDE)

Avoid a heap fetch by including non-key columns in the leaf pages.

```sql
CREATE INDEX idx_orders_user_covering
    ON orders(user_id, status) INCLUDE (total_cents, created_at);
```

Useful for hot lookup queries. Trade storage for fewer I/O ops.

### Other index types (quick reference)

| Type          | Use case                                              |
| ------------- | ----------------------------------------------------- |
| Hash          | Equality only (rarely useful in Postgres — B-tree is fine) |
| GIN           | Full-text search, JSONB, array containment            |
| GiST          | Geometry, range types, full-text                      |
| BRIN          | Huge tables where rows are physically clustered by time (logs, events) |
| Partial       | `WHERE deleted_at IS NULL` — half the size           |
| Expression    | `INDEX ... ON users(lower(email))` for case-insensitive lookup |

### Indexes you should always have

- Every PRIMARY KEY (automatic).
- Every FOREIGN KEY.
- Every column in a `WHERE` clause that filters > 1% of rows.
- Every column in an `ORDER BY` for the top-N queries you actually run.

## 5. Constraints

### NOT NULL

The cheapest constraint. Use it aggressively. If a column is logically required, mark it required.

```sql
email TEXT NOT NULL
```

### UNIQUE

Enforces no duplicates. Combined with NOT NULL it makes a natural key.

```sql
email TEXT NOT NULL UNIQUE
```

For multi-column uniqueness:

```sql
CREATE UNIQUE INDEX uq_org_user_email ON users(org_id, email);
```

### CHECK

Domain validation.

```sql
status TEXT NOT NULL CHECK (status IN ('draft', 'sent', 'failed')),
amount_cents BIGINT NOT NULL CHECK (amount_cents >= 0)
```

### Foreign keys

Already covered above. Use them. The "performance" argument against FKs in 2026 is wrong — the planner is smarter than you.

### DEFERRABLE constraints

For circular FKs or batch loads where order matters:

```sql
ALTER TABLE a ADD CONSTRAINT a_b_fk FOREIGN KEY (b_id) REFERENCES b(id) DEFERRABLE INITIALLY DEFERRED;
```

## 6. Putting it together

A well-modelled OLTP table:

```sql
CREATE TABLE orders (
    id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id         BIGINT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    status          TEXT   NOT NULL CHECK (status IN ('cart','paid','shipped','cancelled')),
    total_cents     BIGINT NOT NULL CHECK (total_cents >= 0),
    currency_code   CHAR(3) NOT NULL,
    placed_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at      TIMESTAMPTZ
);

CREATE INDEX idx_orders_user_id    ON orders(user_id);
CREATE INDEX idx_orders_status     ON orders(status) WHERE deleted_at IS NULL;
CREATE INDEX idx_orders_placed_at  ON orders(placed_at DESC);
```

Every column has a purpose. Every constraint is named. Every FK has an index. The `deleted_at IS NULL` partial index keeps the hot index small.

That is the bar. Now let's build real systems.
