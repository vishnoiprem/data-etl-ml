## 1. What this role really is

This is not only a BI leader and not only a data-platform architect. It is effectively a three-plane mandate:

1. **Business data plane** — trusted metrics for Product, Engineering, Marketing, Sales, Customer Success, Finance, and executives.
2. **Product data plane** — high-volume test execution, logs, traces, screenshots, environments, defects, requirements, releases, and quality signals.
3. **AI data plane** — governed training/evaluation data, retrieval context, features, feedback, lineage, and safe model operations for AI-powered testing.

The winning interview thesis is:

> Build one governed data foundation with distinct workload paths: streaming for live operational insight, a durable lakehouse for history and ML, a curated warehouse/semantic layer for trusted decisions, and a separately governed AI context plane. The organization succeeds when data ownership, quality contracts, privacy, and adoption are designed with the platform—not bolted on later.

## 4. Domain model: learn this before designing

A candidate who models the domain early will sound substantially stronger than one who jumps to Kafka or Snowflake.

### Core hierarchy

```text
Account / Tenant
└── Organization or Workspace
    └── Project
        ├── Requirement
        ├── Test Case ── Test Case Version
        ├── Test Suite
        ├── Release / Sprint / Build
        ├── Defect
        └── Execution
            ├── Test Result (test case + attempt)
            │   ├── Step Result
            │   ├── Log / Trace
            │   ├── Screenshot / Video / Attachment
            │   └── Failure Analysis / Human Feedback
            └── Environment
                ├── OS / Browser / Device
                ├── Region / Agent
                └── Configuration
```

### Recommended grains

| Data product | Grain | Stable key |
|---|---|---|
| Execution fact | One execution attempt | `tenant_id + execution_id + attempt_id` |
| Test-result fact | One test-case attempt within an execution | `tenant_id + execution_id + test_case_id + attempt_id` |
| Step-result fact | One step attempt | Above key + `step_id + step_attempt` |
| Artifact manifest | One artifact version | `tenant_id + artifact_id + version` |
| Requirement-test bridge | One effective-dated relationship | tenant, requirement, test case, valid-from |
| Defect link | One observed link between result and defect | tenant, result, defect, link-time |
| AI analysis | One model/prompt evaluation for a result | result key + `analysis_version` |
| Experiment exposure | One unit’s first qualifying exposure | experiment, variant, unit, exposure-time |

### Invariants to state aloud

- `tenant_id` is mandatory in every key, event, table, index, cache, retrieval filter, and audit record.
- Event time and ingestion time are separate.
- A test result can be retried; “latest” is not equivalent to “only.”
- Test case definitions and environment configuration change, so historical facts reference immutable versions.
- Large artifacts live in object storage; analytical tables store manifests, metadata, hashes, and governed pointers.
- AI analysis is versioned by model, prompt, retrieval policy, input snapshot, and safety configuration.
- User-visible metrics specify whether canceled, skipped, incomplete, retried, or quarantined results count.

### Canonical event envelope

```json
{
  "event_id": "01J...",
  "event_type": "test_result.completed",
  "schema_version": 3,
  "tenant_id": "t_123",
  "project_id": "p_456",
  "execution_id": "e_789",
  "aggregate_version": 17,
  "event_time": "2026-08-19T10:15:20.123Z",
  "ingested_at": "2026-08-19T10:15:20.401Z",
  "producer": "execution-cloud",
  "region": "us-east-1",
  "trace_id": "tr_...",
  "classification": "customer-confidential",
  "payload": {}
}
```

Why these fields matter:

- `event_id` enables idempotency.
- `aggregate_version` detects duplicates, reordering, and missing transitions.
- `event_time` supports correct windows; `ingested_at` supports freshness monitoring.
- `schema_version` enables controlled evolution.
- `classification` lets policy enforcement begin at ingestion.
- `trace_id` connects product operations to data observability.

## 5. Flagship system-design question

> Design Katalon’s global data and AI platform for test execution analytics, live monitoring, company-wide BI, flakiness detection, and AI-assisted failure analysis.

### 5.1 Clarifying questions

Ask five to eight, then make assumptions and move:

1. Who are the primary users: testers, engineering leaders, executives, internal analysts, ML systems, or all?
2. What must be real time: live run status, failure alerts, dashboards, or model features?
3. What are current and three-year volumes for runs, result events, artifacts, tenants, and queries?
4. Is strict ordering required per execution, or is eventual correction acceptable?
5. What are retention and residency tiers? Are private SaaS or regional deployments in scope?
6. What tenant-isolation guarantees and enterprise access models are required?
7. Which source is authoritative for test definitions, requirements, defects, identity, billing, and CRM?
8. What availability, freshness, recovery, and deletion SLOs matter?
9. Are customer artifacts permitted as model input, and under what opt-in/BYOK policies?
10. Is this a greenfield build or a migration with zero dashboard downtime?

### 5.2 Functional requirements

- Accept test lifecycle events and uploaded reports from Katalon and external frameworks.
- Support live execution monitoring within seconds.
- Reconstruct the authoritative state of an execution after duplicates, retries, reordering, and delayed events.
- Store and query years of execution history economically.
- Serve project dashboards, custom analytics, executive metrics, and self-service exploration.
- Detect slow, newly failing, repeatedly failing, and flaky tests.
- Supply governed context for failure classification, summaries, root-cause suggestions, and trend insights.
- Integrate product, billing, CRM, support, marketing, and finance data for company decisions.
- Execute access, retention, legal hold, export, and deletion policies.

### 5.3 Non-functional requirements

Illustrative targets to confirm with stakeholders:

| Capability | Candidate SLO |
|---|---|
| Ingestion acceptance | 99.99% monthly availability |
| Live run status | p95 under 5 seconds from accepted event |
| Standard project dashboard | p95 under 2 seconds |
| Certified business data freshness | 95% of critical products by 07:00 local reporting time |
| Event completeness | 99.99% of accepted events durable and replayable |
| Critical metric correctness | Zero known silent material errors; reconciliation controls on every release |

### 5.4 Back-of-the-envelope sizing

Public fact: more than 30,000 teams use Katalon. Everything below is an **interview assumption**:

```text
Assume 10,000 daily active teams
× 20 executions per team per day
× 100 test-case results per execution
= 20 million test-case results/day

Assume 20 lifecycle/step events per test result
= 400 million small events/day
= ~4,630 events/sec average
× 10 peak factor
= ~46,300 events/sec peak

At 3 KB compressed-average payload per event:
~1.2 TB/day before compaction and retention optimization

Assume 5 MB of logs/screenshots/artifacts per execution:
200,000 executions/day × 5 MB ≈ 1 TB/day of unstructured artifacts
```

State what changes the design:

- If peak traffic is 10× higher, increase partitions and isolate hot tenants.
- If artifacts average 100 MB rather than 5 MB, lifecycle policy and tiering dominate cost.
- If live analytics require sub-second joins across many dimensions, a dedicated real-time OLAP serving store becomes justified.
- If most workloads tolerate five-minute freshness, fewer systems may be better.

### 5.6 Why this shape

- **Kafka/MSK** decouples bursty producers and consumers, supports replay, and matches the posting’s streaming signal.
- **Flink or equivalent stateful streaming** handles event-time windows, per-execution state, late events, and incremental quality signals.
- **S3 + an open table format** provides durable, low-cost history, schema evolution, time travel, and multiple compute engines.
- **A real-time OLAP store** is justified only if product dashboards need low-latency slicing at high concurrency. Otherwise, reduce complexity and serve precomputed state plus warehouse queries.
- **A curated warehouse and semantic layer** make company metrics stable and discoverable.
- **Artifact storage is separate** because screenshots, video, logs, and traces have different cost, privacy, retrieval, and retention patterns than columnar facts.
- **The AI plane consumes governed products** rather than scraping arbitrary production stores.

## 6. Deep dive: ingestion, correctness, and replay

### 6.1 Delivery semantics

Do not promise magical end-to-end exactly-once behavior. Prefer:

- At-least-once delivery.
- Idempotent producers when possible.
- Unique `event_id` plus aggregate version.
- Idempotent sink merge keyed by business grain.
- Checkpointed stream state.
- Reconciliation against producer manifests or execution summaries.

“Exactly once” is a property of the **business result**, not just the message broker configuration.

### 6.2 Ordering

Partition by a stable hash of `tenant_id + execution_id`. This preserves order for one execution within a partition but does not guarantee global order. Use `aggregate_version` to identify gaps. A timeout moves an incomplete execution to a provisional state; later events correct it.

### 6.3 Late and out-of-order data

- Use event-time processing with a watermark.
- Keep a hot correction window, such as 24 hours, based on measured lateness.
- Publish dashboards as provisional until the watermark passes.
- Route very late events through correction jobs.
- Version aggregates so caches can invalidate.
- Track `late_event_rate`, `max_lateness`, and `correction_count` by producer.

### 6.4 Schema evolution

- Put contracts in version control.
- Require compatibility checks in producer CI.
- Additive nullable fields are usually backward-compatible.
- Renames are add-copy-deprecate, not in-place changes.
- Breaking changes use a new event type or major schema version.
- Unknown versions go to quarantine, not silent discard.
- Assign an owner and deprecation deadline to every schema.

### 6.5 Poison records and backpressure

- Validate envelope before payload.
- Quarantine failures with error reason and encrypted raw pointer.
- Do not retry deterministic validation errors forever.
- Rate-limit noisy tenants at the edge while preserving contracted capacity.
- Autoscale on consumer lag and processing time, not CPU alone.
- Expose per-tenant ingestion health without leaking other tenants’ volume.

### 6.6 Reconciliation

For every completed execution, compare:

```text
producer-declared result count
vs accepted-event count
vs silver-table distinct result count
vs served-dashboard count
```

Persist the reconciliation status. A dashboard should be able to show “data incomplete” rather than confidently present a wrong pass rate.

## 7. Deep dive: storage, modeling, and serving

### 7.1 Storage zones

| Zone | Purpose | Mutation policy |
|---|---|---|
| Bronze | Immutable accepted events and source snapshots | Append-only; encrypted; restricted |
| Silver | Validated, deduplicated, conformed domain facts | Merge/correct with audit history |
| Gold | User-facing data products and certified aggregates | Contracted schemas and SLOs |
| AI context | Approved chunks, features, embeddings, labels, eval sets | Versioned; tenant-filtered; policy-bound |

Zones do not themselves create governance. Each gold or AI product needs an owner, contract, quality checks, consumers, classification, retention rule, and SLO.

### 7.2 Partitioning and file layout

For high-volume facts, consider coarse time plus bucketed tenant keys rather than raw `tenant_id` partitioning, which can create millions of small partitions.

Example:

```text
day=2026-08-19 / tenant_bucket=037 / part-....parquet
```

Then:

- Cluster or sort by tenant/project and event time.
- Compact small files continuously.
- Watch partition skew from very large tenants.
- Keep mutable recent partitions separate from stable historical partitions.
- Measure scan bytes per successful query and cost per active tenant.

### 7.3 Dimensional model for analytics

```text
fact_test_result
  tenant_key
  project_key
  execution_key
  test_case_version_key
  environment_key
  build_key
  status_key
  event_time_key
  attempt_number
  duration_ms
  queue_ms
  failure_category_key
  is_final_attempt

Dimensions:
  dim_tenant_scd2
  dim_project_scd2
  dim_test_case_version
  dim_environment
  dim_release
  dim_failure_category
```

Use immutable technical keys internally but preserve natural IDs for reconciliation. Slowly changing dimensions matter because plan, segment, ownership, configuration, and taxonomy can change.

### 7.4 Semantic layer

Every critical metric definition should specify:

```text
Name: Final-attempt pass rate
Owner: Product Analytics / Quality domain
Grain: project-day, with drill-down to execution and test case
Numerator: final test-case attempts with status PASSED
Denominator: final attempts with terminal status PASSED or FAILED
Exclusions: canceled, skipped, quarantined, synthetic monitoring projects
Time: execution completion time in project reporting timezone
Freshness: under 15 minutes for product, daily certified for executive reporting
Dimensions: tenant, project, framework, environment, release, plan
Known caveat: rerun behavior can hide first-attempt instability; pair with first-attempt pass rate
```

The caveat is crucial. A team can improve final pass rate merely by retrying more often.

### 7.5 Serving-path choices

| Need | Best first option | When to add complexity |
|---|---|---|
| Live execution status by ID | DynamoDB/Redis materialized state | High fan-out subscriptions or complex filtering |
| Project dashboard under seconds | Pre-aggregates in warehouse or real-time OLAP | High cardinality, arbitrary filters, high concurrency |
| Executive KPI | Certified warehouse table + semantic layer | Almost never serve directly from streaming state |
| Data science exploration | Lakehouse query engine | Add specialized compute for large feature generation |
| AI retrieval | Metadata store + vector/lexical index + object pointers | Use multimodal index only after eval proves value |

## 8. Deep dive: multi-tenancy, security, privacy, and compliance

### 8.1 Defense in depth

```text
Identity → tenant-aware authorization → service policy → row/object policy
         → encryption context → query audit → anomaly detection
```

Controls:

- Authenticate users and workloads separately.
- Derive tenant context from trusted identity claims, never request-body text alone.
- Enforce tenant predicates in the data-access layer and storage policy.
- Use short-lived workload credentials and separate production roles.
- Encrypt at rest and in transit; isolate keys for high-risk tiers where justified.
- Tokenize or hash joinable identifiers; do not hash low-entropy secrets as if that anonymizes them.
- Use signed, short-lived artifact URLs after authorization.
- Scan logs, screenshots, traces, and test data for secrets/PII before AI indexing.
- Audit reads as well as writes for sensitive data.
- Run automated cross-tenant negative tests in CI and production canaries.

### 8.2 GDPR/CCPA deletion flow

```text
Verified request
    ↓
Identity-to-subject resolution
    ↓
Deletion plan from lineage + retention registry
    ↓
Transactional stores ─ Lake/warehouse ─ search/vector index ─ caches ─ artifacts
    ↓                    ↓                 ↓                 ↓        ↓
tombstone/event      equality delete   document delete   purge    object delete
    └────────────────────── evidence + retries + exception ledger ─────────────┘
                                      ↓
                              signed completion record
```

Key interview points:

- Define controller/processor responsibilities with Legal and Security.
- Maintain purpose, lawful basis/consent where applicable, data category, location, retention, and downstream processors in the catalog.
- Backups need an approved expiry strategy; deletion may be logical until backup rotation completes.
- Legal holds override normal deletion only through an auditable policy.
- Rebuilt derived data, features, embeddings, and caches must not resurrect deleted subjects.
- Train models on appropriately approved data. If deletion from a trained model is not technically guaranteed, document the legal and product policy rather than bluffing.

### 8.3 AI-specific threats

Customer test content is untrusted input. Logs, scripts, HTML, and requirement text may contain prompt-injection instructions or secrets.

Mitigations:

- Treat retrieved text as data, never as system instruction.
- Separate system policy from customer context structurally.
- Limit tools by tenant, role, action, and object; use read-only defaults.
- Require confirmation for mutations with broad impact.
- Redact secrets and high-risk PII before model submission.
- Filter retrieval on authorized tenant/project before scoring, not after top-k retrieval.
- Log model, prompt, retrieved document IDs, safety actions, and outcome—not raw sensitive content by default.
- Validate structured outputs against a schema and business rules.
- Defend downstream renderers against generated HTML/script injection.
- Maintain kill switches by feature, tenant, provider, and model.

## 9. AI-ready platform and failure-analysis design

### 9.1 Start with the task, not with “RAG”

Example task: for a failed test result, predict a failure category, summarize evidence, propose next diagnostic action, and cite the relevant execution artifacts.

Define outputs:

```json
{
  "category": "ENVIRONMENT_ISSUE",
  "confidence": 0.82,
  "summary": "...",
  "evidence_refs": ["log:lines:120-148", "trace:request:77"],
  "next_actions": ["..."],
  "abstain": false
}
```

### 9.2 Pipeline

```text
Failed result
   ↓
Context policy: tenant, project, opt-in, classification, retention
   ↓
Deterministic preprocessing
  - normalize stack trace
  - secret/PII scan
  - extract error codes, selectors, timing, environment
  - compare with recent passes/failures
   ↓
Candidate retrieval
  - same test history
  - similar signatures
  - linked defects/requirements
  - approved documentation
  - lexical + vector ranking with tenant filter
   ↓
Model orchestration
  - structured prompt
  - bounded context
  - schema-constrained output
  - abstention rule
   ↓
Post-validation
  - citations exist
  - suggested actions allowed
  - category valid
  - safety checks
   ↓
Result + user feedback + evaluation log
```

### 9.3 Why hybrid retrieval

- Stack traces, error codes, test IDs, and selectors often need exact lexical matching.
- Natural-language descriptions and semantically similar symptoms benefit from embeddings.
- Recency, environment, test lineage, and same-tenant history are ranking features.
- A cross-encoder or LLM reranker may improve relevance but adds latency and cost.
- The correct design is whichever wins on a representative evaluation set—not whichever sounds most fashionable.

### 9.4 Evaluation framework

Build a stratified, versioned evaluation set across:

- Product area and test framework.
- Failure category.
- Common and rare errors.
- Short and extremely long contexts.
- New and recurring failures.
- Languages and regions where relevant.
- Sensitive-data and adversarial prompt-injection cases.
- Tenants that permit evaluation use, with appropriate de-identification and access.

Metrics:

| Layer | Metrics |
|---|---|
| Retrieval | recall@k, MRR/nDCG, exact evidence coverage, cross-tenant leakage = 0 |
| Classification | macro-F1, per-class precision/recall, calibration, abstention quality |
| Generation | groundedness, citation correctness, actionability, harmful suggestion rate |
| Product | analysis acceptance, time to triage, time to verified fix, repeat usage, override rate |
| Reliability | p50/p95 latency, timeout rate, fallback rate, provider error rate |
| Economics | cost per completed analysis, tokens/artifact bytes, cache hit rate |
| Safety | secret exposure, PII leakage, prompt-injection success, unauthorized tool action |

Do not optimize acceptance rate alone; users may accept plausible but wrong output. Include verified resolution or expert adjudication in the gold set.

### 9.5 Deployment and monitoring

- Register model, prompt, retrieval, and preprocessing versions together.
- Shadow new versions before exposing output.
- Canary by tenant or project with rollback.
- Compare against a deterministic baseline.
- Monitor input distribution, label/feedback distribution, confidence calibration, and slice regressions.
- Route low-confidence or policy-sensitive cases to abstention/human review.
- Cache only when the full policy and version key match.
- Set per-tenant budgets and degrade gracefully: shorter context → smaller model → asynchronous result → deterministic fallback.

### 9.6 Agent architecture judgment

An agent should have the smallest possible action space. Separate:

```text
Planner (proposes)
  ↓
Policy engine (authorizes tenant, user, tool, object, action)
  ↓
Typed tools (read test, read result, search history, draft change)
  ↓
Confirmation gate for mutations
  ↓
Executor + immutable audit
```

For high-impact actions—deleting assets, changing tests broadly, opening external defects—use explicit confirmation and idempotency tokens.

## 10. Flakiness, anomaly detection, and recommendation systems

### 10.1 Flakiness is not simply failure rate

A test that always fails is reliably broken, not flaky. Useful signals include:

- Pass/fail transition rate across comparable runs.
- Entropy of outcomes.
- Failure rate conditioned on environment, code version, time, and dependencies.
- Retry recovery rate.
- Duration variance and tail changes.
- Shared failure signatures across tests.

One transparent score:

```text
transition_rate = status changes between adjacent comparable runs / possible transitions
outcome_entropy = -p(pass)log p(pass) - p(fail)log p(fail)
retry_recovery = failed first attempts that pass on retry / failed first attempts retried

flakiness_score = calibrated_model(
  transition_rate,
  outcome_entropy,
  retry_recovery,
  environment sensitivity,
  duration instability,
  sample size
)
```

Apply shrinkage or a Bayesian prior for small samples. Show an uncertainty interval. Avoid marking a test highly flaky after two runs.

### 10.2 Leakage traps

- Using a retry outcome to predict whether the original attempt is flaky when that retry was not available at decision time.
- Random row splits that place the same test case in train and validation.
- Features computed using future releases.
- Labels generated from a later human classification without point-in-time joins.

Prefer time-based splits and, when testing generalization, hold out projects or tenants.

### 10.3 Recommendation use cases

- Rank which tests to run for a code change.
- Recommend likely duplicate failures.
- Suggest missing coverage for a requirement or API change.
- Prioritize flaky tests by engineering cost and release risk.
- Recommend the next diagnostic action.

For test selection, optimize expected defect-detection value under a time budget, with coverage and safety constraints. Never let optimization silently exclude regulatory, security, or critical-path tests.

## 12. Experimentation platform design

### 12.1 Core objects

```text
experiment_definition
assignment
exposure
eligible_population
metric_observation
analysis_snapshot
decision_record
```

### 12.2 Assignment versus exposure

Assignment says what variant a unit should receive. Exposure says the unit actually encountered the feature. Log exposure only when the relevant UI/API/AI path is rendered or invoked. Analyze intent-to-treat as primary; exposure-based analysis is useful but can introduce selection bias.

### 12.3 Choosing the randomization unit

For collaborative testing software, randomizing individual users may contaminate results because a project shares tests and outputs. Depending on the feature, use project, organization, or account as the unit. Then compute standard errors at that clustered unit.

### 12.4 Guardrails

For an AI failure-analysis experiment:

- Primary: reduction in median time to a verified triage decision.
- Quality: expert-rated correctness and citation validity.
- Safety: cross-tenant leakage and unsafe-action rate must remain zero/within strict policy.
- Reliability: analysis timeout and product error rate.
- Economics: cost per resolved failure.
- Ecosystem: no increase in repeated reruns or support tickets.

### 12.5 Common statistical traps

- Peeking repeatedly without sequential-testing correction.
- Sample-ratio mismatch.
- Novelty effect.
- Unit mismatch between assignment and analysis.
- Triggered analysis that conditions on post-treatment behavior.
- Multiple metrics without false-discovery control.
- Heavy-tailed enterprise usage dominated by a few tenants.
- Network effects within shared projects.
- Shipping a statistically significant but economically irrelevant change.

At Head level, say how decisions are recorded and how you stop experiments, not just how you calculate a p-value.

## 14. Platform selection: how a Head of Data should answer

If asked “Snowflake, Databricks, BigQuery, or Redshift?” do not give a brand-first answer.

### Evaluation matrix

| Criterion | Questions |
|---|---|
| Workloads | BI concurrency, streaming, feature generation, notebooks, unstructured data, low-latency serving? |
| Scale shape | Steady or bursty, many small tenants or a few huge, data size, joins, retention? |
| Ecosystem | AWS integration, Kafka, Airflow, dbt, catalog, identity, BI, ML tooling? |

| Economics | Compute/storage separation, idle cost, egress, concurrency, predictability, commitments? |
| Portability | Open formats, exit cost, SQL compatibility, metadata ownership? |

### Example recommendation style

> Given AWS preference, mixed BI and ML workloads, and large unstructured artifacts, I would first make S3 with an open table format the durable system of record. ### What not to do

- Do not use one database for every workload merely to simplify the diagram.
- Do not create both a lakehouse and warehouse without a clear ownership and synchronization model.
- Do not benchmark only a full table scan; use representative joins, tenant filters, concurrency, updates, and small queries.
- Do not ignore network egress, storage duplication, observability, people, and migration cost.

### 15.2 SQL question: identify unstable tests

> For each tenant/project/test/environment over the last 30 days, calculate run count, failure rate, adjacent status-transition rate, and retry recovery rate. Return only groups with at least 10 comparable executions.

Snowflake-style solution:

```sql
WITH base AS (
  SELECT
    tenant_id,
    project_id,
    test_case_id,
    environment_hash,
    execution_id,
    attempt_id,
    status,
    completed_at,
    ROW_NUMBER() OVER (
      PARTITION BY tenant_id, project_id, test_case_id,
                   environment_hash, execution_id
      ORDER BY attempt_id
    ) AS attempt_rank,
    ROW_NUMBER() OVER (
      PARTITION BY tenant_id, project_id, test_case_id,
                   environment_hash, execution_id
      ORDER BY attempt_id DESC
    ) AS reverse_attempt_rank
  FROM test_results
  WHERE completed_at >= DATEADD(day, -30, CURRENT_TIMESTAMP())
    AND status IN ('PASSED', 'FAILED')
),
first_attempts AS (
  SELECT
    tenant_id,
    project_id,
    test_case_id,
    environment_hash,
    execution_id,
    status,
    completed_at,
    LAG(status) OVER (
      PARTITION BY tenant_id, project_id, test_case_id, environment_hash
      ORDER BY completed_at, execution_id
    ) AS previous_status
  FROM base
  WHERE attempt_rank = 1
),
execution_outcomes AS (
  SELECT
    tenant_id,
    project_id,
    test_case_id,
    environment_hash,
    execution_id,
    MAX(IFF(attempt_rank = 1 AND status = 'FAILED', 1, 0)) AS first_failed,
    MAX(IFF(reverse_attempt_rank = 1 AND status = 'PASSED', 1, 0)) AS final_passed,
    COUNT(*) AS attempt_count
  FROM base
  GROUP BY 1, 2, 3, 4, 5
),
stability AS (
  SELECT
    tenant_id,
    project_id,
    test_case_id,
    environment_hash,
    COUNT(*) AS run_count,
    AVG(IFF(status = 'FAILED', 1.0, 0.0)) AS first_attempt_failure_rate,
    AVG(
      IFF(previous_status IS NULL, NULL,
          IFF(status <> previous_status, 1.0, 0.0))
    ) AS transition_rate
  FROM first_attempts
  GROUP BY 1, 2, 3, 4
),
recovery AS (
  SELECT
    tenant_id,
    project_id,
    test_case_id,
    environment_hash,
    SUM(first_failed) AS failed_first_attempts,
    SUM(IFF(first_failed = 1 AND attempt_count > 1 AND final_passed = 1, 1, 0))
      AS recovered_on_retry
  FROM execution_outcomes
  GROUP BY 1, 2, 3, 4
)
SELECT
  s.*,
  r.recovered_on_retry / NULLIF(r.failed_first_attempts, 0)::FLOAT
    AS retry_recovery_rate
FROM stability s
JOIN recovery r USING (tenant_id, project_id, test_case_id, environment_hash)
WHERE s.run_count >= 10
ORDER BY s.transition_rate DESC, s.run_count DESC;
```

What to discuss after writing it:

- This uses first attempts for transitions so retries do not artificially create flakiness.
- `environment_hash` reduces mixing unlike environments but may fragment data.
- Equal timestamps need a deterministic tie-breaker.
- Missing executions and status taxonomy require explicit policy.
- A production score needs uncertainty/shrinkage and possibly time decay.
- Cluster/partition pruning and pre-aggregation matter at billion-row scale.

### 15.4 Python question: deduplicate out-of-order result events

> Given a finite batch of result events, return the latest event for each business key. Prefer the largest aggregate version; if versions tie, prefer the latest ingestion time. Reject cross-tenant or malformed keys. What changes for an unbounded stream?

Reference solution:

```python
from __future__ import annotations

from dataclasses import dataclass
from datetime import datetime
from typing import Iterable


@dataclass(frozen=True)
class ResultEvent:
    tenant_id: str
    execution_id: str
    test_case_id: str
    attempt_id: int
    aggregate_version: int
    ingested_at: datetime
    status: str

    @property
    def key(self) -> tuple[str, str, str, int]:
        return (
            self.tenant_id,
            self.execution_id,
            self.test_case_id,
            self.attempt_id,
        )


def latest_results(events: Iterable[ResultEvent]) -> dict[tuple, ResultEvent]:
    latest: dict[tuple, ResultEvent] = {}

    for event in events:
        if not event.tenant_id or not event.execution_id or not event.test_case_id:
            raise ValueError("tenant, execution, and test-case IDs are required")
        if event.attempt_id < 0 or event.aggregate_version < 0:
            raise ValueError("attempt and version must be non-negative")

        current = latest.get(event.key)
        candidate_order = (event.aggregate_version, event.ingested_at)
        current_order = (
            (current.aggregate_version, current.ingested_at)
            if current is not None
            else None
        )

        if current_order is None or candidate_order > current_order:
            latest[event.key] = event

    return latest
```

Complexity: `O(n)` time and `O(k)` memory for `k` unique keys.

For an unbounded stream:

- Partition by tenant/execution key.
- Use checkpointed external state, not an in-process dictionary.
- Define event-time watermarks and state TTL.
- Write idempotently to the sink.
- Treat late versions after TTL as corrections through a separate path.
- Monitor state size and hot keys.
- Protect against a malicious tenant creating unbounded cardinality.

## 17. Model answers to difficult follow-ups

### “Why not put everything in Snowflake/Databricks/Redshift?”

> I would minimize systems, but workload boundaries still matter. Live execution state needs predictable low-latency point reads and frequent updates; large artifacts need object storage and lifecycle controls; certified BI needs governed relational semantics; AI retrieval needs authorized lexical/vector access. One platform may cover several of these, but I would verify it through latency, concurrency, governance, and cost tests. I would add a specialized store only when a measured SLO cannot be met economically.

### “Would you choose a data mesh?”

> I would use federated ownership, not begin with a data-mesh reorganization. Product, go-to-market, finance, and quality domains should own definitions and source contracts. A central platform team should provide ingestion, catalog, policy, quality, observability, and serving standards. I would introduce domain data products gradually where ownership and consumer demand are real. The success measure is faster trusted decisions and fewer incidents, not the number of data products.

### “How do you guarantee exactly once?”

> I would not claim a universal guarantee. I would use at-least-once transport, stable event IDs, per-aggregate versions, checkpointed processing, idempotent merges, and reconciliation. The business invariant—for example one final result per test-case attempt—is enforced at the sink and verified against the execution manifest. External side effects use idempotency keys or an outbox pattern.

### “Why not send the whole log to the LLM?”

> It increases cost and latency, weakens relevance, creates privacy risk, and expands the prompt-injection surface. I would deterministically extract high-signal fields, retrieve related context under tenant policy, include bounded evidence, and keep raw artifacts behind authorized references. I would prove the context strategy with retrieval and end-task evaluations.

### “What is your AI north-star metric?”

> For failure analysis, I would optimize verified reduction in time from failure to correct triage or fix, subject to correctness, safety, reliability, and cost guardrails. Usage and thumbs-up are diagnostic signals, not the ultimate value measure.

### “How hands-on should a Head of Data be?”

> Hands-on enough to review architecture, data models, SQL, experiments, evaluation design, incidents, and cost evidence; not the bottleneck for every implementation. I would use code and design reviews to set the bar, prototype high-risk ideas when useful, and build leaders who own execution.

```text
│   └── observability/developer experience
├── Analytics Engineering & Product Analytics
│   ├── semantic layer / certified metrics
│   ├── experimentation
│   └── embedded decision support
├── Applied ML / AI Data
│   ├── features/retrieval/evaluation
│   ├── model operations
│   └── AI product measurement
└── Governance as a cross-functional function
    ├── domain owners and stewards
    ├── Security / Privacy / Legal
    └── platform-enforced policies
```

The exact reporting lines depend on current team size. Early in the journey, combine roles rather than create four management layers.

### 18.2 Hiring order

Diagnose before hiring, but a common sequence is:

1. Senior data-platform/reliability leader if ingestion and trust are the bottleneck.
2. Analytics engineering leader if metric inconsistency blocks decisions.
3. Product analytics/experimentation depth if roadmap decisions lack causal evidence.
4. ML platform/evaluation leadership when multiple AI product teams need shared foundations.
5. Governance program expertise paired with engineering—not a policy-only silo.

### 18.3 Days 0–30: discover and baseline

- Interview Product, Engineering, GTM, Finance, Security, Legal, Customer Success, and current data-team members.
- Build a decision inventory: which recurring decisions have the highest value and lowest trust?
- Map critical sources, products, consumers, owners, lineage, incidents, cost, and access.
- Baseline freshness, correctness, adoption, incident rate, query performance, and unit cost.
- Inventory AI use cases, datasets, providers, evaluations, opt-in rules, and risks.
- Review team skills, on-call burden, ownership gaps, and roadmap commitments.
- Select one executive metric domain and one AI/product-data lighthouse.

Deliverables: current-state map, risk register, metric dictionary v0, platform SLO proposal, and agreed prioritization principles.

### 18.4 Days 31–60: align and prove

- Publish a 12–18 month strategy with outcomes, milestones, dependencies, and explicit non-goals.
- Establish a data council with decision rights—not a status meeting.
- Assign owners to critical data products and source contracts.
- Implement reconciliation and visible quality status for the first metric domain.
- Build an offline evaluation harness for the lighthouse AI use case.
- Run a representative platform benchmark and cost model before major vendor commitments.
- Define access, classification, retention, and deletion paved roads with Security/Legal.

Deliverables: strategy, target architecture, ownership/RACI, certified metric v1, evaluation baseline, and investment options.

### 18.5 Days 61–90: ship and institutionalize

- Put the first certified metrics into an executive decision workflow.
- Productionize one governed ingestion/data-product path with SLOs and runbooks.
- Shadow or canary the AI lighthouse against a deterministic baseline.
- Launch self-service templates and office hours.
- Finalize team topology, hiring plan, and quarterly objectives.
- Remove or consolidate at least one duplicative/low-value pipeline or dashboard if evidence supports it.

Deliverables: measurable adoption, first reliability trend, one production proof point, and a board/executive-ready roadmap.

### 18.6 Example one-year outcomes

Use placeholders until you know Katalon’s baseline:

- Critical metric products with named owners: `[baseline] → [target]`.
- Critical data products meeting freshness/completeness SLO: `[x%] → [y%]`.
- Mean time to detect and recover from data incidents: `[x] → [y]`.
- Duplicate executive metrics retired: `[x]`.
- Time to onboard a governed new source: `[x days] → [y days]`.
- AI evaluation coverage across priority slices: `[x%] → [y%]`.
- Verified failure-triage time for lighthouse AI feature: `[x] → [y]` with quality guardrails.
- Platform cost per million accepted events/query/active tenant: `[x] → [y]`.

Never invent achievements. In your stories, use numbers you can defend or say what you measured qualitatively.

## 19. Leadership story bank

Prepare six stories, each with Situation, Stakes, Your Decisions, Technical Detail, Conflict, Result, and Learning.

### Story 1: enterprise data strategy

- What fragmented state existed?
- Which decisions were blocked?
- How did you prioritize the first data products?
- What did you stop or defer?
- How did the operating model change?
- Which measurable business outcome followed?

### Story 2: platform reliability incident

- What failed and what was the customer/decision impact?
- How did you contain publication?
- How did lineage and immutable inputs help?
- What technical and organizational root causes existed?
- What control prevented recurrence?

### Story 3: governance without slowing teams

- Which sensitive data or regulatory obligation was in scope?
- What paved road did you build?
- Which controls were automatic?
- How did exceptions work?
- Did developer lead time improve or worsen?

### Story 4: AI product from prototype to production

- What user task and baseline did you define?
- How was the evaluation set constructed?
- What failed offline or during canary?
- How did you manage safety, cost, latency, and feedback?
- What verified outcome—not vanity usage—improved?

### Story 5: disagreement with an executive peer

- What were the competing definitions or priorities?
- Which evidence changed the conversation?
- How were decision rights clarified?
- What compromise preserved trust without weakening correctness?

### Story 6: team transformation

- What capability gap existed?
- How did you restructure, coach, hire, or exit work responsibly?
- How did ownership and on-call change?
- How did team health and delivery outcomes change?

### Head-level answer check

Every story should make clear:

- What **you** decided versus what the team did.
- The alternatives you considered.
- The business and technical trade-off.
- How you influenced peers, not only direct reports.
- A measurable outcome you can substantiate.
- What you would do differently.

## 20. Scoring rubric for mock interviews

Score each dimension from 1 to 4.

| Dimension | 1 — weak | 2 — partial | 3 — strong | 4 — Head-level exceptional |
|---|---|---|---|---|
| Problem framing | Jumps to tools | Some requirements | Clear users, scope, constraints | Reframes around decisions/value; identifies unknowns and non-goals |
| Quantitative reasoning | No scale | Rough numbers | Coherent assumptions and implications | Sensitivity analysis ties scale to architecture and economics |
| Architecture | Boxes without behavior | Main components | End-to-end flow and interfaces | Multiple planes, evolution, migration, ownership, and cost |
| Correctness/reliability | Happy path only | Mentions retries | Idempotency, replay, reconciliation, SLOs | Explicit invariants, provisional states, incident and DR strategy |
| Data modeling | Vague entities | Basic schema | Correct grain, keys, history | Semantics, versions, identity, consumer contracts, evolution |
| Security/privacy | “Encrypt it” | RBAC and PII | Tenant isolation, retention, deletion, audit | Executable policy across artifacts, AI, derived data, and backups |
| AI/ML | Model-first | Basic pipeline | Labels, eval, serving, monitoring | Task economics, calibration, safety, rollout, human/agent controls |
| Trade-offs | One answer | Names alternatives | Makes a reasoned choice | Defines decision criteria and change triggers |
| Leadership | Project manager | Team-level | Cross-functional ownership | Executive influence, org design, sequencing, and change management |
| Communication | Rambling | Understandable | Structured and concise | Adapts depth, states decisions clearly, handles challenge calmly |

Passing target: mostly 3s with at least several 4s in strategy/leadership and platform/AI judgment. Any 1 in tenant isolation, privacy, or fundamental correctness is a serious risk.

## 21. Two-week preparation plan

### Days 1–2: role and product

- Learn Katalon’s public product surface and domain model.
- Prepare the 90-second opening and “why Katalon/why now.”
- Draw the three-plane mandate from memory.

### Days 3–4: flagship architecture

- Practice the complete design in 45 minutes.
- Redraw it in 10 minutes.
- Drill ingestion, replay, lakehouse, hot serving, and cost follow-ups.

### Day 5: SQL

- Solve the flakiness query without notes.
- Practice window functions, SCD joins, sessionization, cohorts, percentiles, and query-performance reasoning.

### Day 6: Python and streaming

- Solve two bounded coding problems.
- Explain how each changes in a distributed unbounded system.
- Review retries, idempotency, state, watermarks, and hot keys.

### Days 7–8: AI/ML

- Design failure analysis and flaky-test prediction.
- Define an evaluation set and adversarial tests.
- Practice build/buy and better-model-versus-cost trade-offs.

### Day 9: product analytics

- Build the metric tree and activation hypothesis.
- Design an account/project-level experiment.
- Drill selection bias, clustering, peeking, and sample-ratio mismatch.

### Day 10: governance

- Draw the deletion workflow.
- Explain classification, access, lineage, retention, and AI prompt-injection defenses.

### Days 11–12: leadership

- Prepare six evidence-based stories.
- Cut each to two minutes, then expand to ten with technical depth.
- Remove any metric you cannot defend.

### Day 13: mock loop

- 45-minute system design.

- 30-minute strategy/executive case.
- Score using Section 20.

### Day 14: tighten

- Revisit only weak dimensions.
- Prepare interviewer questions.

## 23. Day-of cheat sheet

Before any design:

```text
Users → decisions → requirements → scale → grain/schema → architecture
→ correctness → security/privacy → observability/cost → rollout/ownership
```

Never forget:

- Tenant ID everywhere.
- Event time differs from ingestion time.
- Retries change metric meaning.
- Large artifacts are not ordinary rows.
- RAG requires evaluation and authorization before retrieval.
- AI logs/test content are untrusted.
- Exactly-once business outcomes require idempotency and reconciliation.
- A platform needs an operating model.
- A strategy needs explicit non-goals.
- Never invent Katalon’s stack, traffic, or your own impact metrics.

Strong closing sentence:

> My goal would be to make trusted data and safe AI a product capability for Katalon, not a collection of pipelines—measured by faster customer outcomes, better decisions, lower operational risk, and a platform teams can adopt without waiting on the central data group.
